What asymptotic analysis is

Asymptotic analysis describes how an algorithm's resource use (usually running time) grows as the input size n grows. Instead of measuring seconds - which depend on the machine, the language, and the compiler - we count basic operations as a function T(n), and then describe the shape of that function for large n.

It answers questions like "if I double the input, what happens to the running time?" A Θ(n) algorithm roughly doubles; a Θ(n²) algorithm roughly quadruples; a Θ(log n) algorithm barely changes; a Θ(2ⁿ) algorithm squares its running time.

Why constants are ignored

Two versions of the same loop might take 3n or 7n machine instructions depending on the compiler or CPU. That factor is real, but it's a property of the implementation, not the algorithm. Asymptotic notation deliberately ignores it so that comparisons stay meaningful across machines.

More importantly, constant factors can't change which algorithm wins for large inputs. Compare 100n with n²:

However large the constant, the linear algorithm eventually wins - and the gap keeps widening. (Constants still matter in practice when comparing algorithms of the same class; see the "Same class, different constants" exercise.)

Why lower-order terms are ignored

Take T(n) = 4n² + 3n + 20. Watch what fraction of the total each term contributes:

The dominant term is the one that grows fastest - here n². Because 3n/n² → 0 and 20/n² → 0, the lower-order terms become irrelevant for large n. Dropping them and the constant 4 leaves the growth rate: T(n) ∈ Θ(n²).

Big O - an upper bound

f(n) ∈ O(g(n)) if there are constants c > 0 and n₀ such that f(n) ≤ c · g(n) for every n ≥ n₀.

In words: eventually, f grows no faster than g (up to a constant factor). Big O is a claim about an upper bound. It is not "the running time", and it is not automatically "the worst case".

Proof for T(n) = 4n² + 3n + 20 ∈ O(n²): for n ≥ 1, 3n ≤ 3n² and 20 ≤ 20n², so T(n) ≤ 4n² + 3n² + 20n² = 27n². Choose c = 27, n₀ = 1. ✓

Since n² ≤ n³ for n ≥ 1, the same argument shows T(n) ∈ O(n³) - a true but looser statement.

Big Ω - a lower bound

f(n) ∈ Ω(g(n)) if there are constants c > 0 and n₀ such that f(n) ≥ c · g(n) for every n ≥ n₀.

Eventually, f grows at least as fast as g. For T(n) = 4n² + 3n + 20: T(n) ≥ 4n² for all n ≥ 1, so T(n) ∈ Ω(n²) with c = 4. Since n² ≥ n, it is also Ω(n) and Ω(1) - true, but loose.

Ω does not mean "best case". You can state a lower bound on the worst case (e.g. "the worst case of any comparison sort is Ω(n log n)").

Big Θ - a tight bound

f(n) ∈ Θ(g(n)) if f(n) ∈ O(g(n)) and f(n) ∈ Ω(g(n)): there are constants c₁, c₂ > 0 and n₀ with c₁·g(n) ≤ f(n) ≤ c₂·g(n) for all n ≥ n₀.

Θ pins down the growth rate exactly (up to constants). For T(n) = 4n² + 3n + 20: 4n² ≤ T(n) ≤ 27n² for n ≥ 1, so T(n) ∈ Θ(n²). There is exactly one growth class that works - Θ(n³) fails the lower half and Θ(n) fails the upper half.

A function describing the whole running time of an algorithm across all inputs may have no single Θ (insertion sort ranges from linear to quadratic). Each specific case - best, worst, average - is a single function and does have one.

A mathematically valid bound is not the same as the most informative bound. Saying "binary search is O(n²)" is true - and nearly useless. When this app asks for the complexity, it asks for the tightest bound.

The base of a logarithm doesn't matter: log₃ n = log₂ n / log₂ 3, a constant factor. See the visualizer.

Sequential operations: add

for i = 1 to n        // n
    print(i)
for j = 1 to n        // + n
    print(j)

One section finishes before the next begins, so their costs add: n + n = 2n ∈ Θ(n). In general O(f) + O(g) = O(max(f, g)): after adding, keep the dominant term. With different variables, keep both: a loop over n followed by a loop over m is Θ(n + m).

Branches: only one branch of an if/else runs, so for the worst case take the max of the branches, not the sum.

Nested loops: multiply (or sum)

for i = 1 to n        // n
    for j = 1 to n    // × n
        print(i, j)

The inner loop runs completely for each outer iteration: n × n = n². Three nested loops over n give n³; loops over different sizes give nm, nk, nmk.

When the inner bound depends on the outer variable, sum the inner counts instead of multiplying:

for i = 1 to n
    for j = 1 to i    // i iterations
Total = 1 + 2 + ... + n = n(n + 1)/2 = ½n² + ½n ∈ Θ(n²)

Summing is what reveals the surprises: a doubling outer loop with an inner loop of i iterations gives 1 + 2 + 4 + ... < 2n = Θ(n), not n log n; an inner loop stepping by i gives n/1 + n/2 + ... + n/n = Θ(n log n). A nested loop is also not always n²: if the inner loop's total work across the whole run is bounded (each item pushed and popped once), the total can be linear - that's amortized analysis.

Logarithmic loops

i = 1
while i < n
    i = i * 2

After k iterations i = 2ᵏ. The loop stops when 2ᵏ ≥ n, i.e. k = log₂ n. The same happens when the problem is divided each step (i = i / 2, binary search, removing a digit with div 10).

Additive updates (i + 1, i + 2, i + 100) → linear. Multiplicative updates (i × 2, i ÷ 3) → logarithmic. Squaring (i × i) → log log n.

A log loop inside an n loop is n log n; two nested log loops are log² n. A loop that runs while i·i ≤ n is √n.

Recursion basics

Write a recurrence: T(n) = (number of calls) × T(subproblem size) + (work done outside the calls). Then unroll it or draw the recursion tree.

function mystery(n)
    if n <= 1
        return
    mystery(n - 1)
T(n) = T(n - 1) + c = T(n - 2) + 2c = ... = T(1) + (n - 1)c ∈ Θ(n)
RecurrenceSolutionExample
T(n) = T(n - 1) + cΘ(n)recursive sum, factorial
T(n) = T(n / 2) + cΘ(log n)binary search, fast power
T(n) = T(n - 1) + cnΘ(n²)quicksort worst case
T(n) = T(n / 2) + cnΘ(n)geometric series: n + n/2 + ...
T(n) = 2T(n / 2) + cΘ(n)visiting every node of a balanced tree
T(n) = 2T(n / 2) + cnΘ(n log n)merge sort: cn work on each of log n levels
T(n) = 2T(n - 1) + cΘ(2ⁿ)two calls on n - 1: the tree doubles each level

Count the calls that actually execute: binary search has two recursive calls in its code but only one runs per invocation.

Best, average, and worst case

For many algorithms the running time depends on which input of size n you get. Each case is its own function of n:

  • Worst case W(n) - the maximum time over all inputs of size n.
  • Best case B(n) - the minimum.
  • Average case A(n) - the expected time under a stated input distribution.
AlgorithmBestAverageWorst
Linear searchΘ(1)Θ(n)Θ(n)
Binary searchΘ(1)Θ(log n)Θ(log n)
Selection sortΘ(n²)Θ(n²)Θ(n²)
Insertion sortΘ(n)Θ(n²)Θ(n²)
QuicksortΘ(n log n)Θ(n log n)Θ(n²)
Cases and bounds are independent ideas. O, Ω and Θ describe functions; the case tells you which function. "The worst case of linear search is Θ(n)" is precise. "Ω means best case" and "O means worst case" are misconceptions - you can put an O, Ω or Θ bound on any case.

What is true: an upper bound that holds for every input must cover the worst case, and a lower bound that holds for every input can be no larger than the best case. That's why insertion sort's running time over all inputs is O(n²) and Ω(n) - with no single Θ.

Pseudocode convention

The Pseudocode Lab runs your code against test cases, so it uses one consistent convention - but it is forgiving about common variations.

procedure Name(A, target)          // also: function, algorithm
    count = 0                      // also: count ← 0, count := 0, set count to 0
    for i = 0 to length(A) - 1     // inclusive bounds; also "downto" and "step 2"
        if A[i] == target          // = also works in conditions; then/do optional
            count = count + 1      // also: count++, count += 1, increment count
        else if A[i] < 0
            ...
        else
            ...
    while low <= high
        mid = floor((low + high) / 2)
    for each x in A
        ...
    swap(A[i], A[j])               // also: swap A[i] and A[j]
    B = new array[n]               // n zeros
    return count
  • Blocks are defined by indentation (end-markers like end if are allowed and ignored).
  • Arrays are 0-indexed and bounds-checked: reading A[n] is an error, just like in a real program.
  • Operators: and or not mod div, == != < <= > >= (≤ ≥ ≠ also work), ^ for powers, / for real division.
  • Functions: length(A) (or A.length), floor ceil sqrt abs min max, append(L, x), print.
  • Constants: true false infinity null.

Example - "return the number of even values in an array":

1. Input: an array of integers. 2. Output: a count (integer). 3. Track: a counter. 4. Iteration over every element + selection (is it even?). 5. Steps:
procedure CountEven(numbers)
    count = 0
    for i = 0 to length(numbers) - 1
        if numbers[i] mod 2 == 0
            count = count + 1
    return count
6. Trace [4, 7, 10]: count 1 → 1 → 2. Returns 2 ✓ 7. One pass, O(1) per element → Θ(n).

Most beginner algorithms follow the same skeleton: initialize → iterate → test → update → return.
